# 请求全链路归档设计

## 1. 背景

当前项目已经具备消费日志能力，核心入口是 `model.RecordConsumeLog(...)`，底层落到 `logs` 表，用于记录请求级元信息，例如用户、模型、配额、token 消耗、请求 ID、分组、渠道等。

这套日志适合做运营统计和问题排查，但不满足以下新需求：

1. 记录用户发给网关的完整请求。
2. 记录网关转发给上游的完整请求。
3. 记录网关收到的上游完整响应。
4. 记录网关最终返回给用户的完整响应。

对这个项目而言，这是一个典型的网关审计能力，而不是普通消费日志能力。

## 2. 目标

新增一套“请求全链路归档”能力，覆盖一个大模型请求在网关内部的完整生命周期。

每个逻辑请求至少需要归档以下四个阶段：

1. `client_request_in`
   用户到网关的原始请求。
2. `upstream_request_out`
   网关转换后发往上游的请求。
3. `upstream_response_in`
   网关收到的上游响应。
4. `client_response_out`
   网关返回给用户的最终响应。

同时需要支持：

1. 普通 JSON 请求。
2. 流式响应，例如 SSE。
3. 渠道重试场景。
4. 错误响应场景。
5. 可检索、可筛选、可按保留期清理。

## 3. 非目标

第一阶段不建议直接覆盖以下场景：

1. WebSocket Realtime 全量逐帧审计。
2. 超大文件上传内容的完整二进制归档。
3. 直接把所有完整 body 永久写入 `logs` 表。
4. 以数据库大字段为唯一存储方式保存所有原文。

这些场景可以在后续阶段扩展。

## 4. 现状分析

### 4.1 当前已有能力

1. 请求 ID 已经存在，可作为逻辑链路主键的一部分。
2. 网关已具备请求体缓存能力，`common.GetBodyStorage(...)` 可以重复读取用户请求体，并且支持内存/磁盘双模式。
3. 项目已有磁盘缓存设施，但现有 `body cache` 是临时缓存，生命周期随请求结束清理，不适合直接作为长期审计归档。
4. 当前 `logs` 表已经记录消费元信息，但不保存完整上下游报文。

### 4.2 当前缺口

1. 没有独立的审计归档表。
2. 没有统一的出站请求拦截层。
3. 没有统一的响应复制与归档层。
4. 对流式响应没有“边转发边归档”的公共组件。
5. 没有脱敏策略和保留期策略。

## 5. 总体方案

建议新增一套独立的“请求审计归档”子系统，而不是复用 `logs` 表。

### 5.1 设计原则

1. `logs` 继续用于运营与消费日志，不承载完整报文。
2. 完整报文归档使用单独表，与 `logs` 表一对一关联。
3. 第一阶段直接入库，不引入额外文件存储。
4. 所有写入默认异步化，避免阻塞主请求链路。
5. 报文原样存储，不做脱敏处理。
6. 必须兼容 SQLite、MySQL、PostgreSQL，数据库字段统一使用 GORM 可移植类型，避免使用 MySQL 专属或 PostgreSQL 专属特性。

### 5.2 核心对象

按第一阶段诉求，数据模型不需要拆成 `trace + event` 两层，直接使用单表即可。

建议新增一张独立表：

1. `log_request_audit`
   一条大模型请求对应一行，通过 `log_id` 与现有 `logs` 表关联，专门保存完整请求与完整响应。

这样更适合当前目标：

1. 实现简单，迁移成本低。
2. 直接复用现有使用日志查询结果。
3. 只关注大模型请求，不额外抽象成通用事件系统。
4. 更容易先落地验证价值。

## 6. 数据模型设计

### 6.1 单表：`log_request_audit`

建议字段：

1. `id`
2. `log_id`
   关联 `logs.id`，一条使用日志对应一条完整归档记录。
3. `request_id`
   当前网关已有请求 ID，便于独立检索。
4. `upstream_url`
5. `retry_count`
6. `client_request_raw`
    保存用户到网关的完整请求，推荐结构：`{"header": {...}, "body": ...}`。
7. `upstream_request_raw`
    保存网关转发到上游的最终请求，推荐结构：`{"header": {...}, "body": ...}`。
8. `upstream_response_raw`
    保存网关收到的上游最终完整响应，推荐结构：`{"header": {...}, "body": ...}`。
9. `client_response_raw`
    保存网关实际返回给用户的最终完整响应，推荐结构：`{"header": {...}, "body": ...}`。
10. `created_at`
11. `updated_at`

说明：

1. `user_id`、`channel_id`、`token_id`、`group_name`、`origin_model_name`、`upstream_model_name`、`request_path`、`request_method`、`is_stream`、`status_code`、`error_type`、`error_code` 等字段，优先直接从 `logs` 表与请求上下文中获取，不在 `log_request_audit` 冗余存储。
2. `log_request_audit` 的职责只保留 `logs` 中没有的“完整报文”信息，以及少量补充字段如 `upstream_url`、`retry_count`。

建议索引：

1. `uniqueIndex(log_id)`
2. `index(request_id)`
3. `index(created_at)`

### 6.2 字段类型建议

此表只需要一张，但四个完整报文字段会很大，因此应直接使用适合大字符串的类型。

推荐原则：

1. GORM 字段类型统一定义为 `text`。
2. MySQL 上让 GORM 落为 `longtext` 更稳妥，避免普通 `text` 容量不足。
3. PostgreSQL 可映射为 `text`。
4. SQLite 仍使用 `text`。

如果实现时需要精确控制 MySQL 大字段类型，可在模型 tag 中显式声明对应类型，并为非 MySQL 数据库提供兼容回退。

### 6.3 为什么这里接受大文本字段

你当前的目标不是做通用审计系统，而是给大模型网关补“完整请求/完整响应留档”能力。

在这个目标下，单表直接存四段大文本有几个现实优势：

1. 查询简单。
2. 联表关系简单。
3. 落地快。
4. 对于日志排障最直接。

因此第一阶段不需要引入额外事件表。

## 7. Body 存储策略

完整请求与响应可能非常大，尤其是：

1. 多轮消息长上下文。
2. 图像 Base64。
3. 流式 SSE 聚合结果。
4. 错误情况下的长上游响应。

但基于当前需求，第一阶段仍然建议优先直接入库，以简化设计和查询路径。

### 7.1 推荐策略

1. 四个报文字段默认直接入库。
2. 存储格式统一为 JSON 字符串，例如：

```json
{
  "header": {
    "content-type": "application/json"
  },
  "body": "..."
}
```

3. 如果未来观测到数据库体积或 I/O 压力明显上升，再演进为文件化存储。

### 7.2 推荐归档目录

第一阶段可以不引入单独归档目录。

如果后续确认数据库存储压力过大，再扩展为“数据库 + 文件”的混合方案。

## 8. 采集点设计

### 8.1 用户到网关请求：`client_request_in`

采集位置建议放在控制器入口之后、真正开始 relay 之前。

对当前项目，最佳位置在 `controller.Relay(...)` 中，完成 `helper.GetAndValidateRequest(...)` 之后即可归档：

1. 读取 `common.GetBodyStorage(c)` 获取原始 body。
2. 记录用户请求头、方法、路径、查询参数。
3. 记录当前用户、token、group、request_id。

优点：

1. 已经具备完整上下文。
2. 读取请求体不会破坏后续处理，因为 BodyStorage 支持重复读取。

### 8.2 网关到上游请求：`upstream_request_out`

采集位置建议不要散落在各个渠道 helper 中手工埋点，而是统一放在 HTTP 客户端传输层。

推荐做法：

1. 为 `service/http_client.go` 中的默认 `http.Transport` 外层包装一个自定义 `RoundTripper`。
2. 在 `RoundTrip(req)` 中记录：
   - 最终 URL
   - 最终 Method
   - 最终请求头
   - 最终请求 body
   - 当前 `request_id`
   - 当前 `attempt_no`

这样可统一覆盖 OpenAI、Claude、Gemini、Embedding、Rerank、Audio、Image 等基于 HTTP 的出站路径。

### 8.3 上游到网关响应：`upstream_response_in`

同样建议在自定义 `RoundTripper` 中处理。

普通响应：

1. 读取响应头和状态码。
2. 复制最终响应 body，写入 `upstream_response_raw`。

流式响应：

1. 第一阶段不需要逐 chunk 归档。
2. 只需要在流式输出结束后，得到完整聚合结果，再写入 `upstream_response_raw`。
3. 如果中途中断，则记录已接收到的最终聚合内容和中断状态。

### 8.4 网关到用户响应：`client_response_out`

这是最容易遗漏的一层。仅记录上游响应还不够，因为项目会对上游数据做格式转换、错误包装、响应裁剪与兼容适配。

推荐做法：

1. 新增 `AuditResponseWriter`，包装 Gin 的 `ResponseWriter`。
2. 在 relay 入口中为当前请求替换 `c.Writer`。
3. 对 `WriteHeader`、`Write`、`WriteString` 做拦截并聚合最终输出。
4. 流式响应不要求逐块记录，只要求最终输出完成后，把最终完整响应写入 `client_response_raw`。

这样才能记录“网关最终返回给用户的响应”，而不是仅记录上游返回。

## 9. 重试与多阶段关系

当前 relay 流程支持重试，但在单表设计下，不需要把每次尝试都拆成独立事件。

第一阶段建议：

1. 表中只保留最终成功或最终失败的那组完整上下游报文。
2. 单独记录 `retry_count`。
3. 如有需要，可额外增加一个 `retry_history` 文本字段保存摘要，例如失败渠道 ID 和错误码列表。

这样更符合“只关注最终完整请求与最终完整响应”的目标。

## 10. 原样存储策略

按当前需求，完整报文原样存储，不做脱敏处理。

约束如下：

1. `header` 原样保存。
2. `body` 原样保存。
3. JSON 不做字段级掩码。
4. 前端查看详情时直接展示原文；如果是合法 JSON，则按格式化 JSON 展示。

这意味着该能力仅适合管理员使用，后续接口和页面权限必须至少限定为管理员可见。

## 11. 流式响应设计

SSE 是这个项目最关键的特殊场景。

### 11.1 目标

1. 不影响首包延迟。
2. 不破坏当前 SSE 转发逻辑。
3. 归档内容与用户实际收到的数据一致。

### 11.2 推荐实现

1. `upstream_response_in`：对流式上游响应做聚合，完成后写入完整结果。
2. `client_response_out`：对流式下游输出做聚合，完成后写入完整结果。
3. 补充记录：
   - 是否流式
   - 是否完整结束
   - 是否异常中断

### 11.3 为什么要同时记录上下游流

因为项目会做协议转换，例如：

1. OpenAI 兼容格式转换。
2. Claude / Gemini 到 OpenAI 兼容格式转换。
3. 错误包装。

只记录上游流无法还原“用户到底收到了什么”。

## 12. 配置项设计

建议新增环境变量：

1. `REQUEST_AUDIT_ENABLED`
   总开关。
2. `REQUEST_AUDIT_MAX_BODY_MB`
   单条归档最大 body 大小。
3. `REQUEST_AUDIT_RETENTION_DAYS`
   保留天数。
4. `REQUEST_AUDIT_CAPTURE_HEADERS`
5. `REQUEST_AUDIT_CAPTURE_BODY`
6. `REQUEST_AUDIT_CAPTURE_STREAM`
7. `REQUEST_AUDIT_SAMPLE_RATIO`
    采样比例，默认 1.0。

第一阶段建议默认：

1. 关闭总开关。
2. 开启后默认全量采集。
3. 对 body 大小做硬限制。

## 13. 对现有模块的改造建议

### 13.1 新增模块

建议新增：

1. `model/log_request.go`
2. `service/request_audit_transport.go`
3. `middleware/response_audit.go`

### 13.2 `model` 层

新增一个模型并在 `migrateDB()` 中加入 AutoMigrate。

### 13.3 `service` 层

新增审计服务，负责：

1. 归档对象生命周期管理。
2. 完整报文写入。
3. retention 清理。

### 13.4 `http client` 层

为默认 transport 包装自定义 `RoundTripper`，统一采集出站与入站上游报文。

### 13.5 `controller` / `middleware` 层

1. relay 入口记录 `client_request_in`。
2. 自定义 `ResponseWriter` 记录 `client_response_out`。

## 14. API 与查询设计

后续建议新增管理接口，而不是直接把完整报文塞回现有 `/api/log` 列表。

建议接口：

1. `GET /api/request_audit/:log_id`
   按 `log_id` 查询完整归档。

筛选项建议支持：

1. `request_id`
2. `user_id`
3. `channel_id`
4. `model_name`
5. `status_code`
6. `is_stream`
7. `start_timestamp`
8. `end_timestamp`

## 15. 前端页面设计

### 15.1 入口位置

在现有“使用日志”列表中，每条大模型请求增加一个按钮：

1. 按钮文案：`查看请求详情`
2. 放置位置：沿用当前列表最右侧“详情”区域，作为该行的一个操作按钮。
3. 仅当该条 `logs` 记录存在对应 `log_request_audit` 数据时显示可点击；没有归档数据时置灰或隐藏。

### 15.2 打开方式

推荐使用弹窗或抽屉，不建议跳转到新页面。

原因：

1. 当前使用日志是典型列表排查场景。
2. 用户需要快速点开、查看、关闭，再继续看下一条。
3. 不应打断当前筛选条件和分页位置。

推荐交互：

1. 点击 `查看请求详情`
2. 打开右侧抽屉或大尺寸弹窗
3. 顶部显示基础信息：`request_id`、模型、用户、渠道、时间、状态码
4. 下方使用四个 Tab 展示四段完整报文

### 15.3 展示内容

四个 Tab：

1. `用户请求`
   对应 `client_request_raw`
2. `上游请求`
   对应 `upstream_request_raw`
3. `上游响应`
   对应 `upstream_response_raw`
4. `用户响应`
   对应 `client_response_raw`

每个 Tab 内部建议统一结构：

1. Header 区域
2. Body 区域

如果存储内容是：

```json
{
  "header": {...},
  "body": ...
}
```

则前端按以下规则展示：

1. `header` 单独格式化显示。
2. `body` 如果是合法 JSON，则按 JSON 格式化显示。
3. `body` 如果不是合法 JSON，则按纯文本显示。
4. 对超长文本区域提供滚动和复制按钮。

### 15.4 JSON 格式化规则

前端展示层处理即可，不要求后端额外返回格式化结果。

建议逻辑：

1. 尝试 `JSON.parse`
2. 成功则按 2 空格缩进格式化显示
3. 失败则原样文本显示

### 15.5 列表联动方式

前端列表本身仍然由 `/api/log/` 提供。

新增详情按钮的建议实现：

1. 列表接口返回每条日志的 `id`
2. 点击按钮后调用 `GET /api/request_audit/:log_id`
3. 返回该条日志对应的四段完整报文

这样前端不需要改动现有使用日志列表的数据来源，只是额外增加一个详情查询接口。

## 16. 与现有 `logs` 表的关系

这套能力不应替代 `logs`，而应与其并存。

建议职责划分如下：

1. `logs`
   面向运营统计、消费记录、错误概览。
2. `log_request_audit`
   面向完整请求/响应归档、排障、回放、请求级取证。

也就是说：

1. `RecordConsumeLog(...)` 继续保留。
2. 新增的审计系统不直接修改 `logs` 语义。
3. 两者优先通过 `log_id` 关联，必要时再通过 `request_id` 辅助查询。

## 17. 分阶段实施建议

### Phase 1

先覆盖最核心 HTTP 非流式场景：

1. 新建 `log_request_audit` 表。
2. 与 `logs` 表通过 `log_id` 绑定。
3. 记录用户到网关完整请求。
4. 记录网关到上游完整请求。
5. 记录上游最终完整响应。
6. 记录网关返回用户的最终完整响应。
7. 只覆盖大模型 relay 请求。

### Phase 2

补齐流式能力：

1. SSE 聚合后归档最终结果。
2. 中断状态标记。
3. 超长流式结果大小限制。

### Phase 3

补齐管理面：

1. 查询 API。
2. 管理台页面。
3. retention 清理任务。
4. 采样与开关控制。

### Phase 4

扩展特殊协议：

1. WebSocket Realtime。
2. 失败重试明细归档。
3. 文件化或对象存储后端。

## 18. 风险与权衡

### 17.1 存储膨胀

四段完整报文直接入库，会显著放大表体积，尤其是长对话和流式场景。

解决方式：

1. 设置 retention。
2. 支持采样。
3. 对超长内容截断。
4. 第二阶段再考虑文件化存储。

### 17.2 性能开销

如果同步写盘或同步写库，可能影响网关延迟。

解决方式：

1. 写入异步化。
2. 流式场景只聚合最终结果，不做逐块持久化。
3. 大字段设置合理上限。

### 18.3 安全风险

由于当前方案要求原样存储，请求和响应中的敏感信息会被完整落库。

解决方式：

1. 仅允许管理员访问。
2. 严格限制详情接口权限。
3. 设置保留期自动清理。
4. 数据库备份与导出链路也需要按敏感数据处理。

## 19. 建议结论

建议第一阶段采用“单表 `log_request_audit` + `logs` 关联”的方案。

这是最适合当前项目的原因：

1. 与现有 `logs` 职责分离清晰，但查询路径更简单。
2. 能直接挂到当前使用日志明细之下。
3. 更符合“只关注大模型请求”的当前目标。
4. 能覆盖用户请求、上游请求、上游响应、用户响应这四个关键阶段。
5. 满足 MySQL、SQLite、PostgreSQL 的兼容要求。

如果进入实现阶段，建议先按这个单表方案做最小实现，后续若发现重试明细、超大报文或流式归档能力不足，再升级为更复杂的数据模型。
